## Multi-Profile results

Each Profile is a GeckoView session context (`GeckoSessionSettings.Builder().contextId(...)`), and a Private Tab adds `usePrivateMode(true)`. All of them share one `GeckoRuntime`. The tests mirror the WebView spike on the `spike/multi-profile-webview` branch.

| # | Check | Result |
|---|---|---|
| P1 | Isolation test: A, B, A private and B private each store a cookie and a localStorage key, then all of them plus GeckoView's default context read | ✅ **PASS**, run twice. Each of the four contexts sees only its own `jrny_iso_*` cookie and localStorage key. The default context sees nothing. |
| P2 | Site-level probe cookie (httpbin.org) | ✅ After setting `jrny_probe` in A and B, `httpbin.org/cookies` in B shows only `jrny_probe=profile_B` and B's own `jrny_iso_B` |
| P3 | Data survives restart and reinstall | ✅ After `adb install -r` and relaunch, **Read storage** shows A and B kept their cookies and localStorage. The data was written about 7 minutes before the restart. A force-stop seconds after a write, the case that lost a cookie in WebView, was **not tested**. A private and B private come back empty, as they should. |
| P4 | Active Profile restored at launch | ✅ The app reopened in Profile B |
| P5 | `window.open` popup stays in the opener's Profile (`NavigationDelegate.onNewSession`) | ✅ From A, the popup saw `jrny_iso_A`. From B, the popup saw `jrny_iso_B`. The app has to return an **unopened** session built with the opener's context ID, the same rule as `onNewTab`. |
| P6 | **Delete a Profile while the app runs**: close its Tabs, then `clearDataForSessionContext("jrny-b")` | ✅ **Read storage** right afterwards: B is empty and A is intact. **No restart needed.** WebView refuses to delete a loaded profile (`IllegalStateException: Cannot delete in-use profile`), which is why SPEC defers the wipe to the next cold start. |
| P7 | uBlock Origin in Profile B | ✅ Blocks there too. On edition.cnn.com it blocked 28 requests (19%). Its "blocked since install" counter covers both Profiles, so **an extension's state and settings are shared by all Profiles**. |
| P8 | uBlock Origin in B's Private Tab | ⚠️ Not active, as expected: the install prompt granted no private-browsing access (`PermissionPromptResponse(true, false, false)`). CNN showed ads, and the popup showed "blank.about-scheme" with 0 blocked. The app still opened the popup. Fenix skips this for extensions that aren't allowed in private browsing (`GeckoEngine.onToggleActionPopup`), and the real app must do the same. |
| P9 | Which Profiles an extension can see (`tabs` and `cookies` permissions, `<all_urls>`) | ⚠️ See below |

**What an extension sees across Profiles (P9):**

- **Tabs.** `tabs.query({})` returns every Profile's tabs with their URLs. Each tab has `cookieStoreId` set to `firefox-container-<contextId>`, for example `firefox-container-jrny-a`. `cookies.getAllCookieStores()` lists one store per Profile that has an open tab. **Any extension with the `tabs` permission can see what is open in every Profile.**
- **Cookies.** `cookies.getAll({ storeId: "firefox-container-jrny-b" })` returned **0** cookies while Profile B held several. The default store returned 21 cookies left from earlier tests, so the API itself works. GeckoView partitions Profiles by the origin attribute `geckoViewSessionContextId`, but the cookies API seems to map a `firefox-container-*` store to the separate `userContextId` attribute. So extensions **cannot read or change Profile cookies** through the cookies API. That protects privacy, but cookie-managing extensions such as Cookie AutoDelete won't work in Profiles. This explanation is inferred from the result and from `OriginAttributes` having a separate `geckoViewSessionContextId` field. I didn't trace the code path.
- **Content scripts and `webRequest`** run in every Profile. The bridge's content script ran in all four contexts, and uBlock Origin blocked in both A and B.
- **There is no per-Profile install, enable or settings.** One `WebExtensionController` serves the whole runtime.

## Passkeys

**Setup.** The app declares `CREDENTIAL_MANAGER_SET_ORIGIN` and `CREDENTIAL_MANAGER_QUERY_CANDIDATE_CREDENTIALS`, like Fenix, and both were granted at install. The tablet has `android.software.credentials`, and its only credential provider is Google Password Manager (GPM). **Passkey probe** (`httpbin.org/html?op=webauthn`) calls `navigator.credentials.get()` and `create()` from the page and logs the outcome.

**How GeckoView 160 handles passkeys** ([`WebAuthnTokenManager.java`][watm], [`WebAuthnCredentialManager.java`][wacm]):

1. It tries Android's Credential Manager first, with `setOrigin(<site origin>)`. This works on Android 14 and later, so on every JRNY device.
2. It falls back to Google Play Services FIDO2 when Credential Manager answers "not supported" on `create()`, or finds no passkey on `get()`. Only builds with `MOZILLA_OFFICIAL` set use `Fido2PrivilegedApiClient`. Every other build, ours included, uses the non-privileged `Fido2ApiClient`. That client works only for sites whose Digital Asset Links list the app.

| Check | Without `play-services-fido` | With `play-services-fido` (`-PwithFido=true`) |
|---|---|---|
| `create()` on httpbin.org, Profile B | `SecurityError: The operation is insecure.` after ~0.9 s. No system sheet. | `SecurityError` after ~0.3 s. No system sheet. |
| `get()` on httpbin.org, Profile B | `SecurityError` after ~1.3 s | `SecurityError` after ~0.9 s |
| webauthn.io "Authenticate" | No visible result and no crash on a retry. The first try (15:03) crashed the main process with a native null-pointer dereference on the Gecko thread. **It didn't reproduce**, and I can't attribute it. | No visible result, no crash |

**Interpretation.** No passkey sheet ever appeared, so GPM didn't accept the request. The fast `SecurityError` matches GeckoView mapping a FIDO `SECURITY_ERR` ([`parseErrorResponse`][watm]). The HONOR tablet hides the Play Services log lines that would confirm GPM's refusal. The WebView spike got the explicit version of the same refusal: "Origin is not being returned as the calling app did not match the privileged allowlist". Profiles aren't the cause: Gecko's `IsWebAuthnAllowedInContext` checks the principal and secure context, not the session context ID ([`WebAuthnUtil.cpp`][wautil]).

**What enabling passkeys takes** (checked 2026-11-16):

- **Google Password Manager.** A browser has to be on Google's privileged-apps allowlist. Apply through the [request form][gpm-form] linked from [Make Credential Manager calls on behalf of other parties for privileged apps][priv-doc]. The list is published at [`gstatic.com/gpm-passkeys-privileged-apps/apps.json`][gpm-list]. It has 73 entries, matched by package name plus the SHA-256 fingerprint of the signing certificate. It includes Mozilla's builds and one independent GeckoView browser, **Waterfox** (`net.waterfox.android.release`), so an independent GeckoView app can be approved. Waterfox's maintainer [submitted the form][waterfox-195].
- **Other providers keep their own lists.** Bitwarden's [`fido2_privileged_community.json`][bw-community] already includes GeckoView browsers: IronFox, Iceraven, Fennec F-Droid and WebLibre. Since 2025.10, Bitwarden can also trust an unlisted browser from a prompt. KeePassDX lets users add privileged apps in its settings. Proton Pass relies on Google's list. ([Summary in freedom-browser-android PR #526][freedom-526].)
- **Signing keys matter.** Every allowlist matches the **release signing certificate**. A build signed by F-Droid needs its own fingerprint listed, separately from our GitHub release key. Debug builds like this spike can't be tested against GPM unless their certificate is listed.
- **`MOZILLA_OFFICIAL` gap.** Even with GPM approval, an unofficial GeckoView build uses the non-privileged FIDO2 client for the fallback. A `get()` on a site where the user has no GPM passkey (security keys, hybrid or QR sign-in through Play Services) would still fail. Passkeys stored in GPM or another approved provider go through Credential Manager and don't hit this path. *(Inferred from the source and not tested, because no provider accepts this app.)*
- **ADR 0002.** On Android 14 and later, the Credential Manager path needs no Play Services library. The library only serves the fallback. In this test the app didn't crash without it.

**Current behavior in the spike: "passkeys unsupported".** Until a provider approves the app, the bundled extension's `passkeys-unsupported.js` catches passkey calls. It runs at `document_start` in every page and frame, in every Profile and Private Tab, and uses `exportFunction`, so a page's Content Security Policy can't block it.

| Check | Result |
|---|---|
| `navigator.credentials.get()` / `create()` with `publicKey` | ✅ Rejected at once (0–4 ms) with `NotSupportedError: Passkeys are not supported in this browser yet.`, and reported to the app log as `passkey-blocked` with the origin. Calls without `publicKey` pass through unchanged. |
| `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()` / `isConditionalMediationAvailable()` | ✅ Both resolve `false`. `getClientCapabilities()`, where it exists, reports every capability as `false`. |
| GitHub's login page (strict CSP, normally offers "Sign in with a passkey" and passkey autofill) | ✅ No passkey call was made and no passkey option was shown. GitHub treated the browser as having no passkeys, and password sign-in was unaffected. |
| The first page after a cold start | The app loads its first page only after `ensureBuiltIn` finishes, so the block is in place before any site runs. The real app needs the same ordering. |

The work to do after launch is in [ROADMAP.md](../../docs/ROADMAP.md) under "After v1": the Google request form, listing every release signing certificate, and other providers' allowlists.

## Password managers through Android Autofill (e.g. the 1Password app)

On Android, password-manager apps fill through the **Android Autofill framework**, not through browser extensions.

- **What GeckoView provides.** Focusing GitHub's login field in the spike started an Android Autofill session and sent a fill request to the device's autofill service (Google on the emulator). GeckoView's `Autofill.java` gives each field the page's domain (`setWebDomain`), HTML info and username, email, password or phone hints ([source][gv-autofill]). That's what a password manager needs to match a login to a site.
- **What 1Password does with an unlisted browser.** 1Password's [Android autofill page][op-autofill] names its supported browsers: Chrome, Firefox (including Beta, Nightly and Preview), Edge, Brave, DuckDuckGo, Opera Touch and Vivaldi. Users of unlisted browsers report that it [treats them like an ordinary app][op-community] and offers logins for the browser's package name instead of the website. 1Password staff described no way to add a browser. So the domain GeckoView supplies may be ignored until 1Password adds JRNY to its list. *(Not tested: needs the 1Password app and an account on the device.)*
- **Passkeys from 1Password** go through Credential Manager, and 1Password applies [its own browser approval][freedom-526]. The spike reports passkeys as unsupported anyway (see Passkeys).

After launch, ask 1Password (and Bitwarden and others) to recognize JRNY as a browser for autofill as well as for passkeys. See ROADMAP.md, "After v1".

## Build requirements found

- **`compileSdk` 37.2.** GeckoView 160's AAR metadata refuses `compileSdk` 37.0.
- **Kotlin 2.4.** GeckoView 160 depends on `kotlin-stdlib` 2.4.21. AGP 9.5.1's bundled Kotlin (2.2) can't read it, so the build pins `kotlin-gradle-plugin` 2.4.0. Every GeckoView upgrade can force a Kotlin upgrade like this.

## Not covered

- Optional permission prompts (`onOptionalPrompt`) and update prompts that ask for new permissions.
- Network traffic: what GeckoView sends to Mozilla (AMO, Remote Settings, telemetry) with no Glean set up. This needs a capture.
- A force-stop seconds after a write (the WebView cookie-flush case).
- Real sign-ins in two Profiles (see "Accounts in two Profiles").

## Verdict

**Yes.** A third-party GeckoView 160 app with no Android Components and no Play Services library can install AMO-signed Firefox extensions. It can install them from an AMO URL or from AMO's own install button, then run them (blocking, popups, dashboards, new tabs) and manage them (list, update, disable, enable, uninstall). Extensions survive restarts. The app can bundle its own unsigned built-in extension that messages it both ways. Release GeckoView refuses unsigned extensions.

The app has to build all of the extension UI itself. In this spike that took about 150 lines of Kotlin, without a tab model or an add-on catalog.

**Profiles work in GeckoView**, and in one place better than in WebView: a Profile can be deleted while the app runs, with no wait for a cold start. The cost is that extensions are global. Every Profile gets the same extensions and settings, and an extension with the `tabs` permission can see the URLs open in every Profile. If JRNY adopts GeckoView, the extensions UI must say this clearly. Per-Profile extensions would need one process and runtime per Profile, which this spike did not try.
